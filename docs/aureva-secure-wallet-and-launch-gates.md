# AUREVA 2027 — secure Apple Wallet commissioning and production sign-off

**Event:** Saturday, Jan 23, 2027, 7 PM to Sunday, Jan 24, 3 AM HST. Optional late checkout until 10 AM. **Admission maximum: 200 paid + comp.**
**Safety:** public ticket sales remain closed until live payment, mail, Wallet and inventory commissioning are certified.

## What has been implemented

- The existing \`/ticket/wallet\` endpoint creates signed passes using \`passkit-generator\`.
- A valid \`ticket/wallet?token=...\` link requires a signed ticket token, an active paid or checked-in ticket, and the current waiver.
- The server requires a registered Pass Type ID, Apple Team ID, WWDR chain, Pass Type certificate, corresponding signing key, and private venue name/address.
- An actual iPhone pass cannot be issued until these real credentials are provisioned. Do **not** use a fabricated Apple team ID or self-signed pass certificate.

## Apple Developer (Account Holder/Admin)

1. Open [Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources/identifiers/list). Under **Identifiers**, create or select a **Pass Type ID** registered to the Enter Wild Ones organization. It must begin with \`pass.\` and match the certificate.
2. Under **Certificates**, issue the **Pass Type ID Certificate** for that ID using a CSR generated by your Mac. Download the Apple-issued certificate.
3. Preserve the matching private key created with the CSR (for example in Keychain Access). Export through a secure local workflow as an appropriately encrypted PKCS#12 bundle, then extract PEM material locally with owner-only permissions when installing production secrets.
4. Obtain the current Apple Worldwide Developer Relations (WWDR) certificate from Apple's certificate authority resources. Verify the full chain, expiry dates and signing-key/public-key match before attempting deployment.
5. Keep signing keys out of Git, build logs, screenshots, chat, and ordinary email. Base64 is an encoding **not encryption**. Netlify must mark private key and certificate variables as **secret**, production only, Functions scope.

## Required Netlify production Functions environment variables

| Environment variable | Value origin |
|---|---|
| \`WILDONES_APPLE_PASS_TYPE_ID\` | Registered Apple Pass Type identifier; e.g. only the one Apple actually registered |
| \`WILDONES_APPLE_TEAM_ID\` | Real 10-character Apple Developer Team ID |
| \`WILDONES_APPLE_WWDR_CERT_BASE64\` | Base64 of the Apple WWDR certificate |
| \`WILDONES_APPLE_PASS_CERT_BASE64\` | Base64 of the matching Pass Type certificate (PEM or DER as used by the signer) |
| \`WILDONES_APPLE_PASS_KEY_BASE64\` | Base64 of the matching certificate private key; **secret** |
| \`WILDONES_APPLE_PASS_KEY_PASSPHRASE\` | Only when the key is encrypted; **secret** |
| \`WILDONES_AUREVA_2026_VENUE_NAME\` | **Private real event venue**, known only to organizers and ticket holders |
| \`WILDONES_AUREVA_2026_VENUE_ADDRESS\` | **Private exact postal address**, never place on public promotion or in the repository |
| \`WILDONES_AUREVA_2026_VENUE_INSTRUCTIONS\` | Optional restricted check-in/parking directions |

All certificate-bearing variables must include **Functions** runtime scope. A new Netlify deploy is necessary after setting environment variables. Existing event code checks that both venue name/address exist before building a pass.

## iPhone acceptance criteria

- [ ] Create one properly authorized, active event ticket with current waiver. A public invitation is **not** sufficient.
- [ ] Open its private \`Add to Apple Wallet\` ticket link on the iPhone in Safari. Never share the URL/token publicly.
- [ ] Server returns \`200\` with \`application/vnd.apple.pkpass\`, and the device offers **Add** to Wallet.
- [ ] Check organizer/event, Sat Jan 23 7 PM HST, serial, barcode, and actual **private** venue details.
- [ ] Confirm QR scanner validates the **same ticket**; a refunded, revoked, malformed or other-event token cannot generate a valid active pass.
- [ ] Review whether location is displayed before authorized admission and ensure private venue information is not accidentally published.
- [ ] Record test timestamp, exact deployed SHA, iPhone/iOS version and a redacted pass validation result in the launch runbook.

## Historical-ticket commissioning gate

A SQL reservation count of 0 **does not** prove Netlify Blob historical tickets are zero.

- Use authenticated [Launch Control](https://enterwildones.com/admin/launch) to inspect AUREVA's event-scoped historical tickets and statuses. Reconcile active paid, checked-in, disputed, refund-pending and comp tickets, duplicate user/invitation identities, unresolved holds and payment records. Verify against live Stripe as appropriate.
- The existing protected \`commission_inventory\` action requires **\`ticketSalesOpen=false\`**, **\`approvedCapacity=200\`**, boolean confirmation and the literal **\`COMMISSION AUREVA\`**. It rejects unknown statuses/identities and reconciles all active tickets atomically with the Neon row lock.
- Commission **through Launch Control only** after reviewing actual historical records. Do not manually set SQL \`commissioned=true\` and do not issue new tickets during reconciliation.
- Verify issued + held <= 200 after backfill and again after real-money checkout/refund tests. Opening public sales is a separate explicit owner decision.

## GitHub branch ruleset enforcement

Ruleset [Basic Protection](https://github.com/AstroTat808/enterwildones/rules/23566095) protects main but currently has **zero** required checks. The helper \`scripts/enforce-main-release-checks.py\` audits it and only changes it when called with an authenticated GitHub admin token and explicit confirmation. Its default mode is **read-only**.

\`\`\`bash
python scripts/enforce-main-release-checks.py
python scripts/enforce-main-release-checks.py --apply --confirm ENFORCE-CHECKS
python scripts/enforce-main-release-checks.py --verify
\`\`\`

Never paste GitHub tokens into commands or files: use the local \`GH_TOKEN\` or \`GITHUB_TOKEN\` environment credential and keep it out of history. GitHub ruleset writes require **Administration:write**. Verify the resulting required checks via the Github ruleset UI or script. Existing no-bypass, no-force-push, and PR rules are preserved by the helper.
